# Global rules text (paste into ~/.claude/CLAUDE.md on another computer)

Version 2.3 (2026-10-08). This is the exact "External reviewers" section of the user's global `~/.claude/CLAUDE.md`. "modelsetup.ps1 -Action install" merges it automatically. Edit it here (main copy) and run the update on every computer.

```markdown
## External reviewers (all existing and future projects)

1. These rules apply to every project. The project name used with the review tools is always the name of the current project.
2. At the start of every work day (first session of the day), before any code or plan goes to an external reviewer, show the user the list of reviewers available, with the ownership and the physical location of each one's servers, and get explicit approval of the reviewers to be used that day. Approval is per day and does not carry over.
   Exception decided by the user (2026-10-08): for Codex (OpenAI) and Gemini / Antigravity (Google) do not ask for or verify server locations; show only the owner. The Russia/China/Iran ban below still applies to them and to every other reviewer.
3. Never use a reviewer, service or server that is owned by, or physically located in, Russia, China or Iran. If ownership or location is unknown, treat it as not approved and say so.
4. Plans and designs go as text. Code goes out only after the user approves it in chat, as disjoint shards (no reviewer above 50% of the project). Never send keystores, secrets, tokens or generated data.
5. Never guess reviewer details: if the list of reviewers cannot be read from an installed skill or tool, report it as unknown.
6. Reviewers are run through their CLIs (Codex, Gemini, Ollama) in read-only mode. Install a missing CLI when needed; the user performs every login. Additional models are only proposed (owner, server location, strengths) and are never activated without the user's approval. Classify reviewers by strength and assign each the matching angle.
7. Review debate (rules approved by the user 2026-10-08): give each reviewer a neutral brief of the plan (no stated preference). Round 1 is independent: reviewers do not see each other's output. Every point carries evidence, severity and a falsifiable closing condition; keep a point register and record dropped objections with the reason. Answer every point (accept, reject with reasoning, or clarify). From round 2 share a deduplicated issue list plus the answers, keeping each original critique visible. The author alone never certifies a resolution: a point closes when its closing condition is met or the raising reviewer concedes on evidence. A "real disagreement" is a point still open after the author's answer where the objection is maintained with evidence and the author rejects it with reasoning, or where the facts are disputed or unknown; merge duplicates; an inadequately answered point stays open. Default maximum is 3 rounds (user decision 2026-10-08); go up to 5 only while a high-severity point is still open. Stop early when a round changes nothing material, and after the cap report what is unresolved and why the process stopped. Check every factual claim a reviewer makes before it enters the point register (reviewers hallucinate; a small model invented a "round 3" in the pilot); direct contradictions between reviewers are registered as disputed points. Small local models (1B-4B) are limited to summarizing, removing duplicates and formatting, plus checks on sensitive material that must stay local; never let them critique as equals, vote or settle a dispute, and verify any critique point they raise before use. Escalate immediately to the user any unresolved high-severity or high-impact point (security, data loss, money, safety). Report to the user only the unresolved disagreements.
8. Local reviewer models approved by the user for every computer (Ollama): `gemma3:1b` (Google), `phi4-mini` (Microsoft), `llama3.2:3b` (Meta). Pull them on any new computer after checking free RAM and disk and showing the sizes. Any other model needs a new approval; models from Chinese, Russian or Iranian companies stay excluded unless approved separately.
9. Full guide, setup prompts and debate prompts: `~/.claude/EXTERNAL_REVIEW.md`. Every project (git or local folder, existing or new) keeps a copy named `EXTERNAL_REVIEW.md` in its root, so the setup can be repeated on any other computer. When starting work in a project without it, copy it in.
10. Portable kit: every project also keeps a `review-kit/` folder (scripts `review.py`, `compact.py`, `sync_check.py`, the rules text `global-rules.md`, the full setup prompt `FULL_PROMPT.md`) and a `REVIEW_LOG.md` (change log and open items). Main copy (Google Drive, visible from every computer): `H:\My Drive\Transit\Dev\ModelSetup` (guide, prompts, kit, rules text, global CLAUDE.md copy, settings snapshot, projects list, master log, `INSTALL.md`, `UPDATE.md`, `scripts\modelsetup.ps1`). The kit on this computer, `~/.claude/review-kit/`, is a derived copy. Together they let these rules be installed, continued and edited on any other computer. Known projects and their locations are listed in `PROJECTS.md` in that folder.
11. Git projects: write the guide, kit and log into the working tree only. Do not commit or push them; the project commits them with its next normal commit. Non-git folders simply keep the files.
12. First access to a project each day on each computer (git repository or plain folder): before any work run `python review-kit/sync_check.py <project dir>` and read `REVIEW_LOG.md`. Git: fetch and report ahead/behind, uncommitted files and commits that arrived from other systems. Plain folder: compare with the master copy (drive or network folder) named in `review-kit/sync_source.txt`; if it is not declared, report UNKNOWN and ask the user. Report to the user what was already done (from the log), what is out of sync, and what remains. Never pull, push, overwrite or delete to "fix" a mismatch without the user's approval. A first check of the day is one with no `SYNC-CHECK` line for this computer and date in `REVIEW_LOG.md`.
13. Additional reviewers approved by the user on 2026-10-08 (still subject to the per-day approval in item 2): Grok (xAI, USA), GitHub Copilot CLI (Microsoft / GitHub, USA), Perplexity (USA; Sonar API; questions and plans only, never code) and Mistral / Codestral (Mistral AI, France). None is owned by a vendor from Russia, China or Iran. Server locations are required for them and were found only in third-party sources (xAI: US and EU depending on the model; Perplexity: US; Mistral: EU by default), so show them as "reported, not officially confirmed". API keys and logins are created and set by the user (environment variables `XAI_API_KEY`, `MISTRAL_API_KEY`, `PERPLEXITY_API_KEY`, or a GitHub login for Copilot CLI); never type, print or store keys. Run them only through `review-kit/review.py`.
14. Log discipline: every change to these rules, tools or setup on any computer is appended to `REVIEW_LOG.md` (date, computer name, what changed, status) and every unfinished item is listed under "Open items". The MAIN copy of all of this is the Google Drive folder `H:\My Drive\Transit\Dev\ModelSetup` (on another computer the drive letter may differ), the only folder visible from every computer (user decision 2026-10-08). `~/.claude` and the project copies are derived: edit the main copy first, then propagate with `scripts\modelsetup.ps1` (`-Action update`, `install`, `status`, `publish`; exact steps in `INSTALL.md` and `UPDATE.md` in that folder). If the Drive path is not reachable on the computer, report it and ask for the path instead of skipping silently.
```
